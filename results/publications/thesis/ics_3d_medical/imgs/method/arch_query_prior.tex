% Real cube-face content: a vertebrae_T9 (target, context) pair from
% TotalSegmentator -- full-body scans, so a wide-FOV level shows real
% surrounding anatomy, unlike FLARE22 (abdomen-only, used in an earlier
% version of this figure). target=s0482, context=s0994, loaded directly
% via TotalSegInContextDataset._load_crop (bypasses the random
% target/context pairing, which is not spacing-invariant, so the standard
% DataLoader path can't guarantee the same two subjects at two spacings).
% The SAME pair at two real spacings -- Level 1 = 3mm (wide FOV, torso
% cross-section around the vertebra), Level 2 = 1mm (narrow FOV,
% vertebra fills the frame) -- axial slice with the most foreground voxels,
% axis 2 (verified against axes 0/1, which give sagittal/coronal spine-
% chain strips here, not axial cross-sections -- see
% /tmp .../scratchpad/check_axes.py). Render script:
% /tmp .../scratchpad/render_ts_vert_fixed.py. The Level-2 (crop) pair
% re-crops from NATIVE data with pred_center set to the class's own
% native-space voxel centroid (not the provider's default bbox-cache
% center), AND with ds.crop_jitter forced to 0 -- _load_crop otherwise
% adds random jitter on top of any explicit pred_center, so repeated
% calls with the identical center landed at different, non-reproducible
% positions. That random jitter, not a geometric issue, was the actual
% cause of both earlier bugs here: the black-edge bug (fixed by re-
% cropping instead of post-hoc shifting the raster -- shifting pushed
% real tissue off one edge and padded the vacated side with black) and
% the off-center bug now (with jitter disabled, pred_center alone lands
% within 1% of dead center for both subjects, no correction needed).
% Slice selection is plain max-foreground throughout (same as everywhere
% else in this figure): a "most-centered among slices with enough
% foreground" variant was tried and reverted -- it picked a thin,
% unrepresentative slice near the vertebra's z-extent edge purely for
% its better 2D centering, and the resulting shape no longer read as a
% vertebra cross-section at all. See
% /tmp .../scratchpad/recrop_l2_proper.py.
% Level 1's context image+mask are then shifted right by 30px
% (shift_ctx_wide.py) -- a deliberate,
% non-physical nudge so target's and context's crop boxes sit at visibly
% different coordinates in Column A below, making the point that the two
% are cropped independently rather than from one shared position.

\newcommand{\archimgCtxCT}{ts_vertebra_context_ct.png}
\newcommand{\archimgCtxMask}{ts_vertebra_context_mask.png}
\newcommand{\archimgTgtCTCrop}{ts_vertebra_target_ct_crop.png}

% \hat{y}^t is a continuous sigmoid probability map (methodology_cascade.tex's
% eq:query-prior), not a thresholded binary mask -- so every lane/cube that
% stands for a PREDICTION (not a real ground-truth mask) uses these
% Gaussian-blurred, continuous-valued versions of the target mask. There is
% no binary \archimgTgtMask macro -- nothing in this figure shows the
% target's prediction as a hard mask. Context's own mask (\archimgCtxMask,
% \archimgCtxMaskCrop above) is real ground truth, so it stays binary.
% The Level-2 OUTPUT blur radius (2) is much smaller than Level-1's (4) --
% the refined, finer-level prediction should read as sharper/more
% confident than the coarse one it was cropped from. But Level 2's INPUT
% prior (lane 1, the crop of Level 1's own prediction warped in via
% eq:query-prior) is the CARRIED-OVER coarse prediction, not L2's own
% refined result -- it gets a separate, blurrier radius (7), so the two
% don't look identical even though they're drawn from the same crop.
\newcommand{\archimgTgtMaskCropPrior}{ts_vertebra_target_mask_crop_prior.png}
\newcommand{\archimgTgtMaskSoft}{ts_vertebra_target_mask_soft.png}
\newcommand{\archimgTgtMaskSoftCrop}{ts_vertebra_target_mask_crop_soft.png}

% ---------------------------------------------------------------------------
% Query prior across 2 cascade levels, WITH the model's own input/output flow
% (arch.md §5) -- each level is a compact version of arch_patchset.tex's
% pipeline, but without the encoder/decoder: this figure is about the
% query-prior mechanism, not the backbone, so each of the four lanes
% (target-image, target-PRIOR, context-image, context-mask) routes its cube
% directly into attention, which routes directly to the predicted mask.
% Level 1's prior lane is an empty/dashed placeholder (support-mean, no real
% input yet); level 2's is a real cube, produced by CROPPING level 1's own
% prediction around its centroid. That side-by-side contrast IS the figure's
% point -- the target "catches up" to having a second (mask-like) lane,
% exactly like context always had.
% ---------------------------------------------------------------------------

% Bigger arrows than the shared default -- shared \archflow vocabulary
% (see arch-macros.tex), same "detailed" bucket as arch_patchset.tex
\archarrowset{detailed}

        % mask-like tensor entering fusion, same role as context's mask.

      % ---- lane 2: context image (always real) ----
      \ifthenelse{\equal{\L}{1}}{\node[anchor=east,font=\normalsize] at (-0.2,2.75) {$I^c$};}{}
